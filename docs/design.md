# UltraVNC 定制功能设计文档

> 状态：**需求已确认**，待开始实现。
> 基线：上游 UltraVNC `7bd294a`（2026-10-24）。

## 0. 总体约束

| 项 | 决定 |
|---|---|
| 兼容性 | 只保证我们自己的查看器和服务端之间互通。新功能都要先协商，对端不支持时自动关闭，**不能**影响和原版客户端的基本连接 |
| 平台 | Windows 10 / 11（x64） |
| 网络 | 走互联网，依然只用 VNC 那**一个 TCP 端口** |
| 编译和测试 | 由用户在 Windows + Visual Studio 环境完成 |
| 实现顺序 | ① 复制粘贴文件 → ② 显卡视频模式 → ③ 单窗口 → ④ 声音 |

## 1. 公共基础：扩展消息通道

四个功能都要在同一条连接里传新数据。为了不到处占用 RFB 消息编号，统一用**一个新的双向消息类型**，里面再分子类型：

```
rfbExtMsg (双向)                       // 临时编号 101，位于 81–126 的空闲区间；
  CARD8   type      = rfbExtMsg        // 服务端→客户端方向另选一个空闲编号（实现时核对）
  CARD8   channel                      // 1=文件剪贴板 2=窗口 3=音频 4=视频
  CARD16  subtype
  CARD32  length
  CARD8   payload[length]
```

- **能力协商**：查看器在 `SetEncodings` 里加一个伪编码 `rfbEncodingExtCaps`（临时定为 `0xFFFF8100`）。服务端看到后，回一条 `channel=0` 的能力消息，列出它支持的通道和参数（比如「有 NVIDIA 硬件编码器」「支持 WGC」）。没协商成功的通道一律不发。
- **未知子类型**：收到不认识的子类型，根据 `length` 跳过，保证以后加功能时向前兼容。
- **发送调度（关键）**：服务端现在是「画面消息发完整再发下一条」（`SendRFBMsgQueue`）。新增一个**带优先级的发送队列**：音频 > 输入反馈或控制消息 > 视频 > 文件数据 > 传统画面。大块数据（文件、剪贴板）**拆成 ≤64KB 的分片**，避免一个大消息长时间堵住声音和视频。
- **加密**：要上公网，**必须启用加密**。现有的 TLS / RSA-AES（`vncviewer/ClientConnectionTLS.cpp`、`ClientConnectionRSAAES.cpp`）或 DSM 插件都在传输层，扩展消息会自动受保护。部署文档里会把它列为必选项。

## 2. 复制粘贴文件（双向，延迟传输）

### 2.1 目标
- 本地在资源管理器里 Ctrl+C 文件或文件夹，焦点切到查看器，在远程 Ctrl+V，文件粘贴到远程的当前目录。
- 反过来：在远程 Ctrl+C，到本地 Ctrl+V。
- 文件内容**粘贴时才传**，资源管理器会显示正常的复制进度条，也可以取消。

### 2.2 原理（两个方向对称）
设「源端」是文件所在的一端，「目标端」是要粘贴的一端。

1. 源端剪贴板变化，出现 `CF_HDROP` → 源端枚举文件，展开文件夹，生成**文件清单**（相对路径、大小、修改时间、属性），给每个文件编号，然后发送 `FileClipOffer`。
2. 目标端收到清单 → 用 `OleSetClipboard` 往本机剪贴板放一个自己实现的 `IDataObject`。它提供：
   - `CFSTR_FILEDESCRIPTORW`：清单；
   - `CFSTR_FILECONTENTS`（按 `lindex`）：每个文件对应一个**按需拉取的 `IStream`**；
   - `CFSTR_PREFERREDDROPEFFECT` = 复制。
3. 用户粘贴 → 资源管理器对每个文件调用 `IStream::Read` → 目标端发 `FileClipRead(fileId, offset, len)` → 源端回 `FileClipData` 分片。`IStream` 在后台线程上阻塞等待数据。
4. 取消或出错时，目标端发 `FileClipCancel`；源端关闭文件句柄。

### 2.3 协议（channel = 1）
| subtype | 方向 | 内容 |
|---|---|---|
| `Offer` | 源→目标 | clipSeq，文件数，每个文件：id、相对路径（UTF-8）、大小、时间、属性 |
| `Read` | 目标→源 | clipSeq、fileId、offset、length |
| `Data` | 源→目标 | clipSeq、fileId、offset、数据（zstd 压缩，可选） |
| `Error` / `Cancel` | 双向 | clipSeq、fileId、错误码 |

`clipSeq` 每次复制递增；收到旧序号的请求直接回 `Error`，避免剪贴板已经变了，粘贴出来却是旧文件。

### 2.4 与现有代码的关系
- 扩展剪贴板协议里本来就**预留了 `clipFiles = 0x10` 格式位**（`rfb/rfbproto.h:1046`），但那套协议是「整个同步发送、不能中断」的，不适合传大文件。所以那个位**只用来做能力声明**，真正的数据走上面的分片通道。
- 查看器端放在 `vncviewer/ClientConnectionClipboard.cpp` 一带，新建 `FileClipboard.cpp/.h`；服务端新建 `winvnc/winvnc/vncFileClipboard.cpp/.h`。`IDataObject` / `IStream` 的实现两端共用，放到 `common/` 下。
- 服务端的剪贴板操作必须在**交互式桌面的进程**里执行（winvnc 的用户会话实例），不能在 Session 0 的服务里。

### 2.5 限制
- 单次复制不限制大小；文件总数超过 10,000 或总大小超过 4GB 时，弹窗确认。
- 只支持复制，不支持剪切移动（`CFSTR_PREFERREDDROPEFFECT` 固定为复制）。
- 粘贴进行中连接断开：资源管理器会报「文件读取错误」，已经写了一部分的文件由资源管理器负责处理。

## 3. 显卡视频模式（NVIDIA，H.264 → HEVC）

### 3.1 两种模式分开
| | 办公模式（默认） | 视频 / 游戏模式 |
|---|---|---|
| 画面 | 现有 Tight/ZRLE/Zstd 等，无损或接近无损 | H.264/HEVC 硬件编码，有损 |
| 驱动方式 | RFB 原有的「客户端请求一次、服务端更新一次」 | **服务端主动推流**，固定帧率（30/60fps） |
| 适合 | 文字、表格、代码 | 视频播放、游戏 |

- 在查看器工具栏 / 菜单里放一个「视频模式」开关，**连接过程中可以随时切换**。
- 服务端没有 NVIDIA 硬件编码器时，能力协商里不会出现视频通道，开关显示为灰色。也就是：**没有独显的机器只用传统模式**。

### 3.2 管线
```
服务端                                                     查看器
DXGI Desktop Duplication ─┐                                 
  (D3D11 纹理, 留在显存)     ├→ 颜色转换 (GPU) → NVENC ──┐      
WGC 窗口捕获 (第 3 阶段) ───┘                              │      
                                          H.264/HEVC 码流 ↓      
                            rfbExtMsg(channel=4) ── TCP ──→ D3D11VA 硬件解码 → 交换链呈现
```
- **抓屏**：自己写一个 DXGI Desktop Duplication 路径（`winvnc/winvnc/vncVideoCapture.cpp`）。现在的 `ddengine.dll` 会把画面拷回系统内存，不能用于零拷贝。传统模式继续用原来的路径，不受影响。
- **编码**：**直接接 NVENC SDK**（不用 Media Foundation）。只需要支持 NVIDIA，而 NVENC SDK 的低延迟控制更细：
  - 预设 `P1–P4` 加 `ULTRA_LOW_LATENCY` 调优，不用 B 帧；
  - 码率控制用 CBR，开启**帧内刷新（intra refresh）**代替周期性关键帧；
  - 运行时动态调码率（`nvEncReconfigureEncoder`）。
  - NVENC 头文件属于 NVIDIA Video Codec SDK（MIT 许可），运行时从驱动加载 `nvEncodeAPI64.dll`，不需要额外安装。
- **解码**：查看器用 **D3D11 视频解码（D3D11VA）**，调用 Windows 自带的解码接口，任何显卡厂商都能用；查看器不要求 NVIDIA。没有硬件解码时，回退到 Media Foundation 的软件解码。
- **光标**：视频流里**不画光标**，继续用现有的光标形状和位置消息（`rfbEncodingRichCursor` / `PointerPos`），本地光标不受编码延迟影响。

### 3.3 协议（channel = 4）
| subtype | 方向 | 内容 |
|---|---|---|
| `Start` | 查看器→服务端 | 编码格式（H264/HEVC）、最大分辨率、目标帧率、最大码率 |
| `Config` | 服务端→查看器 | 实际宽高、格式、SPS/PPS(VPS) |
| `Frame` | 服务端→查看器 | 帧号、时间戳、是否关键帧、NAL 数据 |
| `Feedback` | 查看器→服务端 | 收到的最新帧号、解码耗时、请求关键帧 |
| `Stop` | 查看器→服务端 | 切回办公模式 |

切进视频模式后，服务端暂停传统画面更新；切回时发一次完整画面刷新。

### 3.4 互联网环境下的码率控制（关键）
走的是 TCP，丢包时会重传，表现为**延迟增加**而不是花屏。所以控制目标是**不让发送缓冲积压**：
- 服务端监控 socket 的发送缓冲积压量（未确认字节数）和查看器 `Feedback` 回报的帧延迟；
- 积压增加时立刻降码率；积压持续超过阈值，就**丢帧**（不送进编码器，而不是丢已编码的数据），并请求刷新；
- 网络恢复后，码率按 AIMD 方式缓慢回升（线性增加、成倍下降）；
- 码率范围默认 2–30 Mbps，用户可以设上限。

### 3.5 已知局限（如实说明）
- **TCP 不如 Moonlight 的 UDP + FEC**。在丢包明显的网络上玩对延迟敏感的游戏，体验会比 Moonlight 差，这是只用一个 TCP 端口的代价。如果以后需要，可以加一个**可选的 UDP 视频通道**，在同一个端口号上监听 UDP，所以端口号不变，但防火墙需要放行 UDP。这个暂不做。
- 公网访问需要服务端有公网可达的端口（端口映射），或者使用 UltraVNC Repeater。NAT 穿透不在这次范围里。

## 4. 单窗口远控（WGC 窗口级捕获）

### 4.1 目标
- 查看器菜单「选择窗口…」→ 列出远程顶层窗口（图标、标题、进程名）→ 选一个。
- 只传这个窗口的画面，被遮挡也能正确显示；**弹出菜单和对话框要合成进画面**。
- 键盘鼠标只发给这个窗口。
- 窗口最小化：画面显示「窗口已最小化」并提供「还原」按钮。窗口关闭：回到窗口列表。
- 办公模式和视频模式下都能用。

### 4.2 捕获与合成
- 用 `Windows.Graphics.Capture`（C++/WinRT）捕获目标 HWND。Win10 上被捕获的窗口会有黄色边框（已确认可接受）；Win11 上设置 `IsBorderRequired = false` 去掉。
- **弹出窗口合成**：用 `SetWinEventHook(EVENT_OBJECT_SHOW/HIDE/LOCATIONCHANGE)` 跟踪属于同一进程、或者被目标窗口拥有的可见弹出窗口（菜单 `#32768`、下拉框、tooltip、对话框）。给每个弹出窗口单独开一个 WGC 捕获，在 GPU 上按屏幕坐标合成到一张画布上。
- **画布大小** = 主窗口加所有弹出窗口的外接矩形；大小变了就用 ExtendedDesktopSize 通知查看器调整窗口。
- 合成结果是一张 D3D11 纹理：办公模式下回读到内存，交给现有编码器；视频模式下直接送 NVENC。
- 安全桌面（UAC、锁屏）WGC 拍不到，这时显示提示画面。

### 4.3 输入
- 收到鼠标事件 → 画布坐标换算成屏幕坐标 → 如果不在主窗口或弹出窗口范围内，直接**丢弃**。
- 第一次输入前（以及之后每次焦点被抢走时）调用 `SetForegroundWindow` 把目标窗口切到前台，再用 `SendInput` 注入。远程本机的鼠标会被移动，这一点已确认可以接受。
- 键盘只在目标窗口（或它的弹出窗口）是前台时才注入，否则先切前台。

### 4.4 协议（channel = 2）
| subtype | 方向 | 内容 |
|---|---|---|
| `ListReq` / `List` | 双向 | 窗口列表：句柄、标题、进程名、图标（PNG 小图） |
| `Select` | 查看器→服务端 | 句柄；0 = 退出单窗口回到全屏 |
| `State` | 服务端→查看器 | 正常 / 最小化 / 已关闭 / 安全桌面 |
| `Restore` | 查看器→服务端 | 还原最小化的窗口 |

现有的 `rfbSetSW`（`winvnc/winvnc/vncclient.cpp:4108`，按坐标裁剪区域）保留，供原版查看器使用，和新功能互不影响。

## 5. 远程声音（远程本机静音，麦克风暂不做）

### 5.1 采集方案（待第一步验证）
| 方案 | 做法 | 远程静音？ | 代价 |
|---|---|---|---|
| A. 进程级 loopback | `ActivateAudioInterfaceAsync` + `PROCESS_LOOPBACK`（Win10 2004+），采集全部进程 | **待验证**：是否能在静音输出的同时还采集到声音 | 不用装驱动 |
| B. 虚拟声卡 | 安装虚拟音频设备并设为默认输出，从它那里采集；物理声卡自然没声音 | 是 | 驱动需要签名，部署成本高；断开连接后要恢复默认设备 |

**第一步**：写一个小的独立测试程序验证方案 A，由用户在 Win10 / Win11 上跑。A 可行就用 A，不行就用 B。

### 5.2 传输与播放（channel = 3）
- Opus 编码，48kHz 立体声，每帧 20ms，64–128 kbps（通过 vcpkg 引入 `opus`）。
- 发送优先级最高（见 §1）。
- 查看器端：抖动缓冲目标 60–150ms，可以根据网络情况自适应；积压超过 300ms 就丢弃旧数据追上进度。用 WASAPI 共享模式播放。
- 子类型：`Start`（格式参数）、`Data`（序号、时间戳、Opus 包）、`Stop`。
- 协议里预留麦克风方向（查看器 → 服务端）的子类型，但这次不实现。
- 不做严格的音画同步：视频模式下画面和声音各自尽量低延迟。

## 6. 分阶段计划

| 阶段 | 内容 | 验收 |
|---|---|---|
| 0 | 扩展消息通道 + 能力协商 + 优先级分片发送队列 | 新查看器连原版服务端、原版查看器连新服务端，都正常 |
| 1 | 文件复制粘贴（双向） | 单个文件、文件夹、大文件（>4GB）、取消、粘贴中断线 |
| 2a | DXGI 抓屏 + NVENC H.264 + 查看器 D3D11VA 解码 + 模式切换 | 1080p60 本地局域网稳定，无独显时开关为灰色 |
| 2b | 码率自适应 + 丢帧 + HEVC | 用限速工具模拟 5–20Mbps、50–100ms 延迟、1% 丢包 |
| 3 | 单窗口（WGC + 弹出窗口合成 + 输入过滤），接入两种模式 | 菜单、右键菜单、对话框、窗口缩放、最小化、关闭 |
| 4a | 声音采集方案验证程序 | 用户确认选 A 还是 B |
| 4b | Opus 采集、传输、播放 | 播视频时声音连续，延迟 < 200ms |

每个阶段单独提交，由用户编译测试通过后再进入下一阶段。

## 7. 已确认的补充决定

1. **游戏输入**：不做鼠标锁定 / 相对移动，也不支持游戏手柄。视频模式下鼠标照常使用绝对坐标。
2. **视频模式默认参数**：60fps，码率上限 20 Mbps（用户可调），分辨率跟随远程桌面。
3. **多显示器**：视频模式下只传当前选中的一个显示器。
