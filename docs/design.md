# UltraVNC 定制功能设计文档

> 状态：第 0、1、2a、2b、3a 阶段已完成并测试通过；第 3b 阶段代码已完成，待 Windows 上编译测试。
> 基线：上游 UltraVNC `7bd294a`（2026-10-24）。

## 0. 总体约束

| 项 | 决定 |
|---|---|
| 兼容性 | 只保证我们自己的查看器和服务端之间互通。新功能都要先协商，对端不支持时自动关闭，**不能**影响和原版客户端的基本连接 |
| 平台 | Windows 10 / 11（x64） |
| 网络 | 走互联网，依然只用 VNC 那**一个 TCP 端口** |
| 编译和测试 | 由用户在 Windows + Visual Studio 环境完成 |
| 实现顺序 | ① 复制粘贴文件 → ② 显卡视频模式 → ③ 单窗口 → ④ 声音 |

## 1. 公共基础：扩展消息通道（第 0 阶段，已实现）

四个功能都要在同一条连接里传新数据。为了不到处占用 RFB 消息编号，统一用**一个新的双向消息类型**，里面再分通道和子类型：

```
rfbExtMsg（双向，两个方向都是编号 101）
  CARD8   type      = rfbExtMsg (101)
  CARD8   channel   // 0=控制 1=文件剪贴板 2=窗口 3=音频 4=视频
  CARD8   flags     // bit0 = 后面还有分片，bit1 = 这是续片
  CARD8   subtype   // 含义由 channel 决定
  CARD32  length    // 大端序，后面 payload 的字节数
  CARD8   payload[length]
```

- **代码位置**：协议核心在 `common/ExtChannel.h/.cpp`，不依赖 Windows，服务端和查看器共用，单元测试在 `tests/ext_channel/`。服务端接入在 `winvnc/winvnc/vncExtChannel.*`，查看器接入在 `vncviewer/ClientConnectionExt.*`。
- **能力协商**：
  1. 查看器在 `SetEncodings` 里加伪编码 `rfbEncodingExtCaps`（`0xFFFF8100`）；
  2. 服务端看到后，发出自己的 Caps（channel 0，subtype 1）：协议版本、支持的通道位图、可接收的最大分片；
  3. 查看器**收到服务端的 Caps 之后才开始发送** `rfbExtMsg`，并回复自己的 Caps；
  4. 双方取通道位图的交集。没协商成功的通道一律不发。
  - 这样新查看器连原版服务端时，服务端不认识这个伪编码，也就不会发 Caps，查看器就永远不发 `rfbExtMsg`；原版查看器连新服务端时，不会声明这个伪编码，服务端也就不发。两个方向都不会出现原版程序不认识的消息（原版程序遇到未知消息会直接断开）。
- **分片**：超过 64KB 的消息拆成多个分片（`flags` 标记）。同一个 (channel, subtype) 的分片不会和同一个 (channel, subtype) 的另一条消息交错，但不同通道的消息可以插在中间，所以声音这类小包能「插队」到大文件的分片之间。单个分片最大 1MB，重组后的消息最大 32MB，超过就当作协议错误断开连接。
- **向前兼容**：收到不认识的通道或控制子类型，直接忽略；Caps 末尾多出来的字节也忽略。
- **发送调度**：每一端都有一个发送线程和四个优先级队列：音频 > 控制 > 视频 > 批量数据（文件）。服务端发送时持有画面更新锁，所以扩展消息总是在两次画面更新之间发出，不会插进一次更新的中间。每一批次里，音频和控制消息全部发完；视频和批量数据最多发 64KB（默认 256KB，服务端和查看器都设成了 64KB）就释放锁，让画面更新能及时发出去。
  - 同一个 (channel, subtype) 必须一直用同一个优先级，否则分片顺序会乱；代码里会检查并拒绝。
- **测延迟**：协商完成后，双方每 2 秒互发一次 Ping/Pong（channel 0，subtype 2/3），算出平滑后的往返延迟（`RttMicros()`），供第 2 阶段的码率自适应使用。
- **断线和重连**：服务端在客户端线程退出时停止发送线程；查看器在每次连接（包括自动重连）前重置通道状态。
- **加密**：要上公网，**必须启用加密**。现有的 TLS / RSA-AES（`vncviewer/ClientConnectionTLS.cpp`、`ClientConnectionRSAAES.cpp`）或 DSM 插件都在传输层，扩展消息会自动受保护。扩展消息的收发写法和现有扩展剪贴板一致（消息头带类型字节，负载单独发送），所以在非流式 DSM 插件下也能正常工作。

## 2. 复制粘贴文件（双向，延迟传输）（第 1 阶段，已实现）

### 2.1 目标
- 本地在资源管理器里 Ctrl+C 文件或文件夹，切到查看器，在远程 Ctrl+V，文件粘贴到远程的当前目录。
- 反过来：在远程 Ctrl+C，到本地 Ctrl+V。
- 文件内容**粘贴时才传**，资源管理器会显示正常的复制进度条，也可以取消。

### 2.2 原理（两个方向对称）
设「源端」是文件所在的一端，「目标端」是要粘贴的一端。两端都同时扮演这两个角色，代码共用（`common/FileClipboard.*`）。

1. 源端剪贴板变化，出现 `CF_HDROP` → 源端枚举文件，展开文件夹（不进入目录联接/符号链接），生成**文件清单**（相对路径、大小、修改时间、属性），清单里的序号就是文件编号，然后发送 `Offer`。
2. 目标端收到清单 → 过滤掉不安全的路径 → 用 `OleSetClipboard` 往本机剪贴板放一个自己实现的 `IDataObject`。它提供：
   - `FileGroupDescriptorW`：清单（文件夹也在里面，资源管理器会建出空文件夹）；
   - `FileContents`（按 `lindex`）：每个文件对应一个**按需拉取的 `IStream`**；
   - `Preferred DropEffect` = 复制；
   - 私有格式 `UltraVNC FileClip`：标记「这是 UltraVNC 放的虚拟文件」，两端都不会把它再发回去，避免来回循环。
   - 剪贴板变化的发现：注册剪贴板监听，同时每 0.5 秒轮询一次剪贴板序号兜底（某些运行方式下监听通知可能收不到）。
3. 用户粘贴 → 资源管理器调用 `IStream::Read` → 目标端发 `Read`（每次 1MB，**预读最多 8MB**，网络延迟高时也能跑满带宽）→ 源端用 256KB 一片的 `Data` 依次发回。`Read` 在剪贴板线程上等待数据，60 秒没有任何进展就报错。
4. 资源管理器用完一个流（读完、取消或出错）→ 目标端发 `Cancel`，源端关闭文件句柄。
5. 源端剪贴板变成别的东西（不是文件）→ 发 `Revoke`，目标端如果剪贴板上还是这批虚拟文件，就把它们清掉。
6. 连接断开 → 进行中的读取立刻失败，目标端清掉剪贴板上的虚拟文件，源端关闭所有文件。

### 2.3 协议（channel = 1，格式见 `common/FileClipProto.h`）
| subtype | 方向 | 内容 | 优先级 |
|---|---|---|---|
| `Offer` (1) | 源→目标 | seq，条目数，每条：属性、大小、修改时间、UTF-8 相对路径（`/` 分隔） | 批量 |
| `Revoke` (2) | 源→目标 | seq | 批量 |
| `Read` (3) | 目标→源 | seq、streamId、fileId、offset、length（≤16MB） | 控制 |
| `Data` (4) | 源→目标 | streamId、offset、标志（bit0 = 文件结束），后跟数据 | 批量 |
| `Cancel` (5) | 目标→源 | streamId | 控制 |
| `Error` (6) | 源→目标 | streamId、错误码（1 清单已过期，2 文件编号无效，3 打不开，4 读失败，5 打开的文件太多） | 批量 |

- `seq` 每次复制递增；`Read` 带的 seq 不是源端当前的清单，就回 `Error`（清单已过期）。已经打开的文件不受影响，继续读完。
- `streamId` 由目标端分配，每个 `IStream` 一个，`Seek` 到缓冲区以外时换一个新的 id，迟到的旧数据会被丢掉。
- 和顺序有关的消息（`Offer`、`Revoke`、`Data`、`Error`）都走同一个批量队列，保证先后顺序；目标端的小请求（`Read`、`Cancel`）走控制队列，不会排在文件数据后面。
- 没有做压缩（原设计里的 zstd 可选项）：常见的大文件（压缩包、视频、图片）本来就压缩过，以后需要再加。

### 2.4 安全
- **路径校验**（目标端，`IsSafeRelativePath`）：拒绝绝对路径、盘符、`..` 和 `.`、空的路径段、`\`、Windows 禁用字符（`<>:"|?*`、控制字符）、设备名（`CON`、`NUL`、`COM1`…，包括带扩展名的 `nul.txt`）、以点或空格结尾的名字、非法 UTF-8，以及超过 259 个字符（`FILEDESCRIPTORW` 的上限）的路径。不合格的条目直接丢弃，并写日志。
- **只能读清单里的文件**：对端只能按文件编号读取，编号来自最近一次 `Offer`，不能指定任意路径。
- **服务端权限**：只有设置里「允许文件传输」打开、而且该客户端可以操作键盘鼠标时才启用。服务端以服务方式（SYSTEM）运行时，枚举和打开文件都**模拟当前登录用户**；拿不到登录用户的令牌时拒绝。（最初还检查了「工作站已锁定」，但现有的判断方法是看会话里有没有 `LogonUI.exe`，有些系统解锁后它仍然存在，导致远程到本地的复制全部失败，已去掉。）
- **查看器权限**：选了「禁用剪贴板」或「只看模式」时不启用。
- **需要知道的一点**：和 Windows 远程桌面一样，连接期间在任意一端复制文件，对端都会收到文件清单，并且**可以读取这些文件的内容**，不需要这一端的用户真的去粘贴。所以只应该连接你信任的对端。
- **COM 访问权限**：服务端以服务方式运行时，在启动时调用 `CoInitializeSecurity`，允许同一会话里的普通用户进程（资源管理器）调用我们的剪贴板对象，同时用强制完整性标签拒绝低完整性进程。

### 2.5 限制
- 一次复制最多 100,000 个条目，超过就不发送（写日志）。原设计里「超过 10,000 个文件或 4GB 弹窗确认」取消了：因为是粘贴时才传，复制本身没有代价，而在源端复制时弹窗会打扰只是在本机复制文件的用户。
- 相对路径超过 259 个字符的条目会被跳过（资源管理器虚拟文件的限制）。
- 只支持复制，不支持剪切移动。
- 粘贴进行中，在源端又复制了别的文件：已经开始读的文件会读完，还没开始的文件会报错。
- 查看器或服务端以管理员身份（提升权限）运行、而资源管理器是普通权限时，粘贴可能失败（COM 的完整性级别限制）。以服务方式运行的服务端已经处理了这个问题。

## 3. 显卡视频模式（NVIDIA，H.264 → HEVC）

### 3.1 两种模式分开
| | 办公模式（默认） | 视频 / 游戏模式 |
|---|---|---|
| 画面 | 现有 Tight/ZRLE/Zstd 等，无损或接近无损 | H.264/HEVC 硬件编码，有损 |
| 驱动方式 | RFB 原有的「客户端请求一次、服务端更新一次」 | **服务端主动推流**，固定帧率（30/60fps） |
| 适合 | 文字、表格、代码 | 视频播放、游戏 |

- 在查看器工具栏 / 菜单里放一个「视频模式」开关，**连接过程中可以随时切换**。
- 服务端没有 NVIDIA 硬件编码器时，能力协商里不会出现视频通道，开关显示为灰色。也就是：**没有独显的机器只用传统模式**。

### 3.2 管线
```
服务端                                                     查看器
DXGI Desktop Duplication ─┐                                 
  (D3D11 纹理, 留在显存)     ├→ 颜色转换 (GPU) → NVENC ──┐      
WGC 窗口捕获 (第 3 阶段) ───┘                              │      
                                          H.264/HEVC 码流 ↓      
                            rfbExtMsg(channel=4) ── TCP ──→ D3D11VA 硬件解码 → 交换链呈现
```
- **抓屏**：自己写一个 DXGI Desktop Duplication 路径（`winvnc/winvnc/vncVideoCapture.cpp`）。现在的 `ddengine.dll` 会把画面拷回系统内存，不能用于零拷贝。传统模式继续用原来的路径，不受影响。
- **编码**：**直接接 NVENC SDK**（不用 Media Foundation）。只需要支持 NVIDIA，而 NVENC SDK 的低延迟控制更细：
  - 预设 `P1–P4` 加 `ULTRA_LOW_LATENCY` 调优，不用 B 帧；
  - 码率控制用 CBR，开启**帧内刷新（intra refresh）**代替周期性关键帧；
  - 运行时动态调码率（`nvEncReconfigureEncoder`）。
  - NVENC 头文件属于 NVIDIA Video Codec SDK（MIT 许可），运行时从驱动加载 `nvEncodeAPI64.dll`，不需要额外安装。
- **解码**：查看器用 **D3D11 视频解码（D3D11VA）**，调用 Windows 自带的解码接口，任何显卡厂商都能用；查看器不要求 NVIDIA。没有硬件解码时，回退到 Media Foundation 的软件解码。
- **光标**：视频流里**不画光标**，继续用现有的光标形状和位置消息（`rfbEncodingRichCursor` / `PointerPos`），本地光标不受编码延迟影响。

### 3.3 协议（channel = 4）
| subtype | 方向 | 内容 |
|---|---|---|
| `Start` | 查看器→服务端 | 编码格式（H264/HEVC）、最大分辨率、目标帧率、最大码率 |
| `Config` | 服务端→查看器 | 实际宽高、格式、SPS/PPS(VPS) |
| `Frame` | 服务端→查看器 | 帧号、时间戳、是否关键帧、NAL 数据 |
| `Feedback` | 查看器→服务端 | 收到的最新帧号、解码耗时、请求关键帧 |
| `Stop` | 查看器→服务端 | 切回办公模式 |

切进视频模式后，服务端暂停传统画面更新；切回时发一次完整画面刷新。

### 3.4 互联网环境下的码率控制（关键）
走的是 TCP，丢包时会重传，表现为**延迟增加**而不是花屏。所以控制目标是**不让发送缓冲积压**：
- 服务端监控 socket 的发送缓冲积压量（未确认字节数）和查看器 `Feedback` 回报的帧延迟；
- 积压增加时立刻降码率；积压持续超过阈值，就**丢帧**（不送进编码器，而不是丢已编码的数据），并请求刷新；
- 网络恢复后，码率按 AIMD 方式缓慢回升（线性增加、成倍下降）；
- 码率范围默认 2–30 Mbps，用户可以设上限。

### 3.5 已知局限（如实说明）
- **TCP 不如 Moonlight 的 UDP + FEC**。在丢包明显的网络上玩对延迟敏感的游戏，体验会比 Moonlight 差，这是只用一个 TCP 端口的代价。如果以后需要，可以加一个**可选的 UDP 视频通道**，在同一个端口号上监听 UDP，所以端口号不变，但防火墙需要放行 UDP。这个暂不做。
- 公网访问需要服务端有公网可达的端口（端口映射），或者使用 UltraVNC Repeater。NAT 穿透不在这次范围里。

### 3.6 第 2a 阶段实现情况（已完成代码，待 Windows 测试）

| 部分 | 实现 | 和上面设计的差别 |
|---|---|---|
| 抓屏 | `winvnc/winvnc/vncVideoCapture.*`：DXGI Desktop Duplication，选与查看器画面重叠最多的显示器；画面留在显存 | 显示器必须接在 NVIDIA 显卡上（核显输出的笔记本暂不支持）；不支持旋转的显示器 |
| 编码 | `winvnc/winvnc/vncNvencEncoder.*`：NVENC，P4 预设 + 超低延迟调优，CBR，无 B 帧，无限 GOP，按需 IDR；输入直接用 BGRA 纹理，由 NVENC 做颜色转换 | 没用帧内刷新，丢包恢复靠「查看器请求 → 发 IDR」；H.264 最大 4096×4096 |
| 推流 | `winvnc/winvnc/vncVideoStreamer.*`：每个客户端一个线程，按帧率节拍抓取和编码；画面静止时不发任何帧；发送队列积压超过约 3 帧时**在编码前**跳过该帧 | 码率自适应（AIMD）留到 2b，2a 先用固定码率 20 Mbps |
| 解码 | `vncviewer/VideoDecoder.*`：Windows 自带的 Media Foundation 同步（软件）解码器，低延迟模式 | 原设计是 D3D11VA 硬件解码 + 交换链显示；2a 先用软件解码，**直接写进查看器原有的帧缓冲**（libyuv 做 NV12→BGRA），所以缩放、全屏、截图都照常可用。1080p60 软件解码大约占一个 CPU 核的一部分；4K60 可能吃力，硬件解码放到 2b |
| 开关 | 查看器系统菜单「Video Mode (GPU)」 | 原设计是工具栏按钮，先放菜单 |
| 光标 | 视频模式下查看器不再请求画面更新，**远程光标形状也不更新**，只显示本地光标 | 原设计是继续用光标消息；需要在视频通道里补发光标形状，放到 2b |

视频模式下查看器不再发送增量画面更新请求，服务端也就不发传统画面；退出视频模式时查看器请求一次完整画面。

前提：查看器使用 32 位真彩色；服务端缩放为 1/1。不满足时菜单会提示原因。

### 3.7 第 2b 阶段实现情况（已完成代码，待 Windows 测试）

| 部分 | 实现 |
|---|---|
| 码率自适应 | 服务端每 0.5 秒评估一次（AIMD）：出现「因发送队列满而跳帧」或往返延迟比历史最低值高出 150 ms，就把码率降到 70%；连续 2 秒没有拥塞，每次加最大码率的 5%。起始码率为最大值的一半，最低 1 Mbps。往返延迟来自扩展通道的 Ping，服务端改为每 0.5 秒一次。历史最低延迟每 30 秒（在网络平稳时）重新学习一次，以适应线路变化 |
| HEVC | 查看器能**用显卡**解码 HEVC 时自动请求 HEVC（HEVC 软件解码太重，不请求）；服务端显卡不支持 HEVC 编码时自动退回 H.264，`Config` 里告诉查看器实际用的格式。Windows 上 HEVC 解码需要安装应用商店里的「HEVC 视频扩展」 |
| 硬件解码 | 给 Windows 自带的 Media Foundation 解码器设置 D3D11 设备，由它在显卡上解码（任何厂商的显卡）；解出的 NV12 纹理复制到一块 CPU 可读的纹理，再走原来的显示路径。第一帧做完整性检查（读回失败时画面全为 0，正常视频不会出现），出错就在本次连接内改用软件解码并请求关键帧 |
| 光标 | 服务端从 DXGI 桌面复制取得光标形状和可见性，形状变化时发 `Cursor` 消息（单色光标保留 AND/XOR 掩码，所以文本 I 形光标依旧是反色；带掩码的彩色光标近似转成带透明度的彩色）。查看器在视频模式下显示远程光标；远程隐藏光标时（很多游戏）查看器也不显示 |

测试：`tests/video_proto`（协议，含光标消息）、`tests/video_decoder`（在 Wine 里跑：允许 GPU 解码时，Wine 的 GPU 读回会失败，测试验证了自动退回软件解码；强制软件解码时颜色正确）、`tests/video_cursor`（在 Wine 里跑：单色/彩色光标的尺寸、热点、透明、反色）。


## 4. 单窗口远控（第 3a 阶段已实现，待 Windows 测试）

### 4.1 目标
- 查看器菜单「Single Window...」→ 列出远程顶层窗口（标题、程序名）→ 选一个。
- 只传这个窗口的画面，被遮挡也能正确显示；**弹出菜单和对话框合成进画面**。
- 键盘鼠标只发给这个窗口。
- 窗口最小化：查看器询问是否还原。窗口被关闭：回到整个桌面并提示。

### 4.2 拆分
- **3a（已实现）**：完整流程 + **无损分块传输**（只发生变化的 64×64 块，zstd 压缩，文字清晰），**不需要 NVIDIA 显卡**，适合办公。
- **3b（已实现，待 Windows 测试）**：窗口画面走视频模式（NVENC），适合在单个窗口里看视频、玩游戏。见 4.7。

### 4.3 捕获与合成（`winvnc/winvnc/vncWindowCapture.*`）
- 主窗口：`Windows.Graphics.Capture`（自由线程帧池，轮询取帧，不需要事件回调）。WGC 不可用或失败时，自动改用 `PrintWindow(PW_RENDERFULLCONTENT)`（也能抓 DirectX 和浏览器内容，只是更耗 CPU）。日志会写用的是哪一种。
- 弹出窗口：属于目标窗口（所有者链上有它），或者是同一进程的 `WS_POPUP` 窗口（菜单、下拉列表、提示框），并且在 Z 序上位于目标窗口之上。它们本来就在最上层，**直接从屏幕截取**（`BitBlt` + `CAPTUREBLT`，包括带阴影的分层窗口），再合成到画布上。原设计是给每个弹出窗口单独开 WGC 捕获；WGC 对菜单这类系统窗口不一定可用，所以改成截屏。
- 画布 = 主窗口可见区域（DWM 扩展边框范围）和所有弹出窗口的外接矩形；没有被覆盖的地方填深灰色。最大 8192×8192。
- Win10 上 WGC 会给窗口加黄框（已确认可以接受），Win11 上关掉。WGC 的接口在 MSVC 下用 Windows SDK 的头文件（SDK 22000 以前没有关黄框的接口，会自动跳过）。

### 4.4 传输（`common/WindowProto.*`，channel 2）
| subtype | 方向 | 内容 |
|---|---|---|
| `ListReq` / `List` | 双向 | 窗口列表：句柄、进程号、是否最小化、标题、程序名 |
| `Select` | 查看器→服务端 | 句柄；0 = 回到整个桌面 |
| `State` | 服务端→查看器 | 会话号、状态（进行中 / 已最小化 / 已关闭 / 不可用 / 已结束 / 被拒绝）、说明 |
| `Canvas` | 服务端→查看器 | 会话号、画布宽高 |
| `Frame` | 服务端→查看器 | 会话号、帧号、画布尺寸、变化的块列表、zstd 压缩后的像素 |
| `Ack` | 查看器→服务端 | 会话号、帧号 |
| `Restore` | 查看器→服务端 | 还原被最小化的窗口 |

- 最多 30 帧/秒；**流控**：未确认的帧达到 2 帧就先不发，下一帧把期间所有变化一起带上（和传统 VNC 的「请求一次发一次」类似，网速慢时自动降帧）。
- 画布尺寸变化时先发 `Canvas`，然后发完整画面；帧里带着画布尺寸，查看器丢掉尺寸不符的旧帧（但仍然确认，免得流控卡住）。

### 4.5 和传统画面的配合
- 查看器把本地帧缓冲改成画布大小（复用服务端调整分辨率时的处理流程），退出时恢复原来的桌面尺寸，并请求一次完整画面。窗口模式期间远程改了分辨率，查看器会记下新尺寸，退出时用它。
- 服务端在会话开始时清掉这个客户端待处理的画面更新请求，会话期间忽略新的请求，所以**不会有按桌面尺寸编码的旧画面**写进已经变小的帧缓冲。画面更新和扩展消息在同一把锁下发送，先后顺序有保证。
- 3b 起两者可以组合：视频模式开着时选窗口，窗口画面就用视频编码传（见 4.7）。

### 4.6 输入（`winvnc/winvnc/vncWindowSession.*`）
- 鼠标：画布坐标 + 画布原点 = 屏幕坐标，用 `SendInput`（绝对坐标、整个虚拟桌面）注入；**在窗口和它的弹出窗口以外按下的键会被丢弃**，但在窗口里开始的拖动可以拖到外面再松开。支持左/中/右键、滚轮（包括高精度滚轮）、左右键互换设置。遵守原有的「该客户端是否允许操作鼠标」权限。
- 键盘：注入每个按键前，如果前台窗口不是目标窗口或它的弹出窗口，就先把目标窗口切到前台（临时附加到当前前台线程的输入队列以绕过前台锁）。远程机器前如果有人在用电脑，窗口会被切到前台，鼠标也会移动（已确认可以接受）。
- 列出窗口时读取标题用 `InternalGetWindowText`，不会向窗口发消息，所以遇到卡死的程序也不会挂住。

### 4.7 单窗口 + 视频模式（第 3b 阶段）
- **用法**：视频模式开着时选窗口 → 窗口用 NVENC 编码传输；单窗口模式下打开视频模式 → 当前窗口切换成视频；关掉视频模式 → 当前窗口切回无损分块；退出单窗口模式而视频模式还开着 → 恢复整个显示器的视频流。
- **协议**：`Select` 多了一个字节「传输方式」（0 分块 / 1 视频，不带这个字节时按分块处理）；视频通道的 `Start` 用原来保留的字节作为标志位，`kStartParamsOnly` 表示「只记下参数、不推显示器」，单窗口模式下打开视频时用它，避免先推一下整个显示器。
- **服务端**：窗口会话照常抓取和合成画布，但不再发分块，而是在画面**有变化时**把画布交给推流线程（最多 60 次/秒）。推流线程在 NVIDIA 显卡上建 D3D11 设备，把画布上传成纹理后用 NVENC 编码，`Config` 的位置固定为 (0,0)（查看器的帧缓冲就是画布）。节拍、码率自适应、拥塞时编码前丢帧、按需关键帧，和显示器视频流完全共用同一套逻辑。画布尺寸变了（窗口缩放、弹出对话框）就重开编码器、发新的 `Config`。
- **出错退回**：窗口视频编码失败时，推流线程通知窗口会话，会话自动改回无损分块并发送完整画面；查看器收到视频结束的状态后关掉视频模式，窗口继续显示。
- **码率控制抽成共用模块** `common/RateController.*`（有单元测试）。抽取时发现并修正了 2b 的一个问题：原来的「历史最低往返延迟」只在网络平稳时才重新学习，如果线路延迟**永久变高**，会一直被当成拥塞，码率卡在最低。现在参考值取最近 15～30 秒内的最低延迟，旧样本自然过期，最多 30 秒后恢复。
- **PrintWindow 防卡死**：目标程序已经卡死（`IsHungAppWindow`）时不再调用 `PrintWindow`（它会一直等那个程序），继续显示上一帧。

## 5. 远程声音（远程本机静音，麦克风暂不做）

### 5.1 采集方案（待第一步验证）
| 方案 | 做法 | 远程静音？ | 代价 |
|---|---|---|---|
| A. 进程级 loopback | `ActivateAudioInterfaceAsync` + `PROCESS_LOOPBACK`（Win10 2004+），采集全部进程 | **待验证**：是否能在静音输出的同时还采集到声音 | 不用装驱动 |
| B. 虚拟声卡 | 安装虚拟音频设备并设为默认输出，从它那里采集；物理声卡自然没声音 | 是 | 驱动需要签名，部署成本高；断开连接后要恢复默认设备 |

**第一步**：写一个小的独立测试程序验证方案 A，由用户在 Win10 / Win11 上跑。A 可行就用 A，不行就用 B。

### 5.2 传输与播放（channel = 3）
- Opus 编码，48kHz 立体声，每帧 20ms，64–128 kbps（通过 vcpkg 引入 `opus`）。
- 发送优先级最高（见 §1）。
- 查看器端：抖动缓冲目标 60–150ms，可以根据网络情况自适应；积压超过 300ms 就丢弃旧数据追上进度。用 WASAPI 共享模式播放。
- 子类型：`Start`（格式参数）、`Data`（序号、时间戳、Opus 包）、`Stop`。
- 协议里预留麦克风方向（查看器 → 服务端）的子类型，但这次不实现。
- 不做严格的音画同步：视频模式下画面和声音各自尽量低延迟。

## 7. 已确认的补充决定

1. **游戏输入**：不做鼠标锁定 / 相对移动，也不支持游戏手柄。视频模式下鼠标照常使用绝对坐标。
2. **视频模式默认参数**：60fps，码率上限 20 Mbps（用户可调），分辨率跟随远程桌面。
3. **多显示器**：视频模式下只传当前选中的一个显示器。
